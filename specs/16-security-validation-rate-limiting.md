# Security validation and API rate limiting

## Threat and context

TrackRanker exposes public HTTP endpoints without authentication and accepts athlete-entered training prescriptions, notes, repetition evidence, and reflections. Relevant risks include malformed values, meaningless or oversized text, excessive automated reads, resource exhaustion, and abusive repeated writes.

The selected Security Measures advanced requirement consists of two independently useful controls: server-side validation/sanitisation and API rate limiting. Dependency auditing remains a separate maintenance practice and is not counted as one of these measures.

## Security measure 1: Data validation and sanitisation

### API boundary audit

Training-session create and update DTOs enforce:

- controlled `SessionType` and `TrainingSessionStatus` enum values;
- a required session date;
- a required, non-whitespace prescription of at most 1,000 characters;
- an optional custom title of at most 100 characters;
- optional purpose and coach notes of at most 1,000 characters;
- optional focus cue and success criteria of at most 500 characters;
- intended intensity from 0 to 100.

Session-completion create and update DTOs enforce:

- actual intensity and perceived difficulty from 1 to 10;
- set and repetition numbers of at least 1;
- positive distance and time values;
- repetition notes of at most 500 characters;
- each reflection or coach-feedback field at most 1,000 characters;
- confidence-before and confidence-after values from 1 to 5.

ASP.NET Core's `[ApiController]` validation rejects invalid HTTP payloads before controller actions proceed. Services repeat DataAnnotation validation because they are also exercised directly outside MVC in unit tests. New record IDs and timestamps are generated by the backend and are not writable request fields.

### Normalisation

Required and optional athlete text is trimmed at the service boundary. Whitespace-only optional clarity, repetition-note, reflection, and coach-feedback values become `null` instead of meaningless stored strings. A focused `NotWhiteSpaceAttribute` closes the audited gap where a required prescription containing only spaces previously passed `[Required]` before being trimmed empty.

Normal punctuation and sprint notation are preserved. Valid examples include:

- `3 × 150m, 10 min rest`
- `2 sets of 20m – 30m – 30m – 20m at 95%`
- `Stay relaxed through the final 50m.`

TrackRanker does not apply destructive regular-expression filtering, strip apostrophes, or HTML-encode text before persistence. React escapes ordinary rendered text by default, and the application does not introduce raw HTML rendering for athlete content.

## Security measure 2: Rate limiting

TrackRanker uses ASP.NET Core's built-in rate-limiting middleware with two named fixed-window policies:

| Policy | Default | Scope |
| --- | --- | --- |
| `api` | 120 requests per 60 seconds | Public training-session reads, completion reads, Confidence History, and Progress |
| `write` | 30 requests per 60 seconds | Session and completion POST, PUT, and DELETE actions |

Fixed windows are intentionally simple and predictable for the current single-instance application. Queuing is disabled, so an excessive request is rejected immediately rather than holding server resources.

Policies partition requests by `HttpContext.Connection.RemoteIpAddress`, with a stable `unknown-client` fallback when no address is available. TrackRanker does not trust user-controlled `X-Forwarded-For` values. Deployment behind a reverse proxy must configure forwarded headers with known trusted proxies before forwarded client addresses can safely influence partitioning.

Rejected requests return HTTP 429 with a concise JSON body:

```json
{
  "error": "Too many requests. Please try again shortly."
}
```

When the limiter supplies retry metadata, the response includes an accurate `Retry-After` header. It does not expose limiter internals, connection details, or stack traces. The frontend's shared API client also provides understandable 429 wording and does not retry automatically.

### Health and E2E decisions

`GET /api/health` is explicitly exempt. Hosting platforms may poll health frequently, and making operational health checks compete with athlete API traffic would make deployment monitoring fragile.

`POST /api/testing/reset` is also explicitly exempt from public policies so repeated Cypress scenarios remain deterministic. This does not weaken its existing controls: it remains unavailable in Production, returns 404 unless E2E mode is explicitly enabled, accepts no database name, and can operate only on a configured database ending in `_e2e`.

Scalar and OpenAPI endpoints are not assigned a public API policy, preserving the existing Development documentation experience.

## Configuration

Safe defaults live in `ApiRateLimitingOptions` and can be overridden using:

```text
RateLimiting__ApiPermitLimit=120
RateLimiting__WritePermitLimit=30
RateLimiting__WindowSeconds=60
```

Options are validated during startup. Test hosts use lower permit values without waiting for a one-minute production-style window.

## Testing

Backend tests prove that:

- requests below the API limit succeed;
- repeated API requests receive a safe 429 rather than 500;
- the write policy is stricter and separate from read traffic;
- DTO validation still returns 400 before the write limit is exhausted;
- health remains available beyond configured API limits;
- the disabled E2E reset remains guarded and exempt;
- registered defaults are 120 API requests, 30 writes, and 60 seconds;
- whitespace-only required text is rejected;
- maximum lengths are enforced;
- valid sprint symbols and punctuation survive trimming;
- optional completion evidence is normalised without damaging meaningful text.

Frontend coverage verifies clear handling of HTTP 429 responses.

## Dependency audit finding

The current `npm audit` reports one high-severity transitive advisory: `nanoid` 3.3.16 through Vite's PostCSS build-tooling path. The advisory concerns custom generators with a zero size; TrackRanker does not call this API directly. A patched `nanoid` version is available, but no forced or unrelated dependency upgrade is included in this focused milestone. This finding is retained for dependency maintenance and is not counted as a selected security measure.

## Limitations

- Rate limiting is not authentication or authorization.
- Multiple athletes behind one network address may share a partition.
- In-memory limiters are local to one API process; multi-instance deployments may require a shared or gateway-level strategy.
- Correct real-client IP handling behind a reverse proxy depends on deployment-specific trusted-forwarder configuration.
- Limits reduce abusive volume but do not make every malicious request harmless.
- Dependency advisories require ongoing review independently of these two controls.
